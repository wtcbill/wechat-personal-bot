## 2. B1：默认由现有检索模型决定是否搜索

### 已确认的行为

默认使用 `auto`，由现有检索模型结合用户问题、对话历史及实际资料决定搜索、直接进入作答或澄清。取消程序根据自然语言关键词推断 `off / required` 的逻辑。模型通过是否提出工具调用表达决定，无须先把 `auto` 改成 `required`。

保留调用方显式传入的网络策略：

| 请求参数 | 含义 |
|---|---|
| 未传或 `auto` | 允许模型决定是否搜索／读取网页；仍受工具权限和预算限制 |
| `off` | 程序禁止 Search／Fetch；模型 API 仍会联网 |
| `required` | 程序要求取得实际外部证据；缺关键条件时可澄清，无法完成时明确说明 |

显式开关来自调用入口，不从消息文字推断。现有入口如下：

| 入口 | 参数来源与调用链 |
|---|---|
| 独立 `npm.cmd run chat` | [chat CLI](../src/chat/cli.ts) 将 `--offline` 转成 `off`、`--search` 转成 `required`；不带选项传 `auto`，直接调用 ChatService |
| 微信 `npm.cmd start` | [应用](../src/application.ts) 只传会话 ID、请求 ID 和文本，经路由进入 ChatService；没有传 network，使用默认 `auto` |
| 主程序终端 `npm.cmd start -- --debug` | 同样通过 Application 和服务路由；与独立 chat CLI 是不同入口，没有上述网络选项解析 |
| 其他代码调用公共接口 | 可通过 [ServiceRequest.network](../src/services.ts) 显式指定；[路由](../src/router/router.ts) 继续传递并保留澄清期间的既有约束 |

微信里说“不要搜索”属于自然语言要求：在 `auto` 下由模型理解并遵守，不自动生成 `off` 参数。模型可能理解错误；显式 `off` 才是程序强制禁止搜索／抓取的开关。

### 实施位置与步骤

1. 在 [chat/service.ts](../src/chat/service.ts) 删除整个 `policy()` 函数，包括两条文本正则。将 `execute()` 中的调用直接替换为：

   ```ts
   const network = request.network ?? "auto";
   ```

   不再保留仅包装默认值的函数，不新增独立分类模型或决策调用。

2. 在同一文件的 `RESEARCH_PROMPT` 中说明：`auto` 下根据真实意图、上下文、时效性与事实不确定性决定工具使用；区分操作要求与引用、翻译、改写对象，不以词语是否出现作为依据；用户明确要求不搜索时使用已有信息，必要时说明无法核实。

3. 在 `ANSWER_PROMPT` 中补充：`auto` 下用户明确要求不搜索时，也不得请求补查；资料不足时说明限制或澄清，避免作答阶段绕过前面的用户要求。

4. 保留现有参数合法性检查、`off` 的工具执行限制、`required` 的证据检查、引用校验、取消及时间／次数预算。保持公共接口和各入口的参数传递方式。

5. 已同步 [chat L2](../src/chat/L2.md)、[搜索问答方案](Weave搜索问答方案讨论.md) 中的网络策略说明，并核对 [README](../README.md) 的独立 CLI 用法。未改变公共接口与各入口参数传递。

### 验收条件

| 场景 | 预期 |
|---|---|
| 未传 network，问题为“解释搜索算法” | 程序使用 auto，不因“搜索”强制 required；模型应按普通解释任务处理 |
| 未传 network，问题为“今天有什么新闻” | 程序使用 auto；模型应判断需要时效资料并搜索 |
| 显式 auto，问题为“把‘不要联网’翻译成英文” | 参数保持 auto；模型应将引文作为待翻译内容 |
| auto，用户要求“不需要搜索，润色下面的文字” | 模型遵守要求，不搜索／抓取，也不提出补查 |
| 显式 off，问题包含“搜索／联网” | 始终禁止搜索／抓取 |
| 显式 required | 保留本轮外部证据约束及缺关键条件时的澄清路径 |

离线核对实际参数流与执行限制，并在实施后运行适用的类型检查、现有测试及构建。语义判断和真实工具调用另用受控的真实模型样本验证；离线通过不等于模型语义验收通过。不恢复模拟模型、模拟后端或模拟 HTTP 测试。

验收时区分程序默认值、模型决定、实际工具调用和最终结果；不以最终答案自称“已搜索”作为调用证据。不额外增加独立判断调用，但真实搜索次数、耗时和费用可能随模型决定变化。

## 3. B2：同页锚点链接的来源校验

### 本轮范围

用户于 2026-10-23 确认本项改法。范围为修正同页锚点误拦截；本轮忽略“翻译／改写时原样保留用户网址却被拦截”的场景。两个问题的发现证据均保留在审查报告；忽略一个场景不代表它已经修复。

本轮不引入用户原文网址白名单，也不为该翻译场景修改提示词或扩展输出检查的输入。下面只调整已取得来源的 URL 比较规则。

### 当前问题与根因

[research.ts](../src/chat/research.ts) 的 `register()` 通过 [webUrl()](../src/chat/types.ts) 登记来源；`webUrl()` 会执行 `url.hash = ""`，将 `#setup` 等 fragment 去掉。

[chat/service.ts](../src/chat/service.ts) 的 `outputProblems()` 则用 `new URL(...).href` 解析答案网址，保留 fragment，然后要求它与本轮证据的 URL 完全相等。两处处理规则不一致：

| 环节 | 用于比较的值 |
|---|---|
| 已取得的来源 | `https://example.com/help` |
| 答案中指向该页某部分的链接 | `https://example.com/help#setup` |
| 当前字符串比较 | 不相等，报“链接不属于本轮已获取来源” |

这里的 `#setup` 一般用于定位页面中的某个部分。当前代码只做 URL 比较，没有检查对应锚点是否实际存在。误拦截已通过直接执行当前 `outputProblems()` 纯函数离线复现；不是微信显示或网络访问失败。

### 已确认的改法与实施位置

- 输出检查复用来源登记使用的 `webUrl()` 规范化规则，仅将用于比较的答案 URL 去掉 fragment；保留原始答案中的链接，用户仍能使用页内定位。
- 本轮证据列表、来源 ID 检查及其他输出限制继续保留。协议、主机、路径、查询参数不同仍须作为不同 URL 比较，不能仅按同域名放行。
- 此改法只确认链接属于同一个已取得来源的页面，不保证锚点存在，也不证明该页支持答案中的所有结论。进一步验证锚点不纳入本轮范围。

实施时在 [chat/service.ts](../src/chat/service.ts) 从 `./types.ts` 导入已有 `webUrl`；将 `outputProblems()` 内解析比较地址的 `new URL(...).href` 改为 `webUrl(...)`。保留原有链接提取、末尾标点处理、异常处理与后续 evidence 比较，只修改比较用的局部 URL，不改写 `answer`。来源登记处继续使用现有实现。

### 验收条件

- 本轮证据中有该页面时，同页带 fragment 的链接通过 URL 归属检查；不带 fragment 的已有正常链接继续通过。
- 不同路径、查询参数、主机或协议的未登记链接仍被拒绝；本轮没有该页证据时不能因规范化而放行；来源 ID 校验继续生效。
- 最终答案保留原有 fragment，且没有为通过检查而增加搜索／读取调用。

已用真实输出检查纯函数完成离线回归，并以真实 Fetch 后作答核对最终 fragment 保留；类型检查、测试、构建及 chat L2 同步见验证记录。未引入模拟 HTTP／模型，不额外验证锚点存在。

## 4. B3：路由 session 字段严格校验

### 当前问题与影响

路由模型返回 `dispatch` 决定时，`session` 按 [契约](../src/router/types.ts) 只能是字符串 `"new"` 或 `"continue"`，分别表示新建后端会话和继续已有绑定。当前 `parseDecision()` 用下面的条件检查：

```ts
["continue", "new"].includes(String(item.session))
```

它先把值转成字符串做检查，却在返回结果时保留原值；`as "continue" | "new"` 只是 TypeScript 类型断言，不会在运行时转换数据。因此 JSON 中的数组 `["new"]` 会通过校验，返回的 session 仍然是数组。

[router.ts](../src/router/router.ts) 随后用 `decision.session === "new"` 判断是否丢弃旧澄清上下文、创建新后端会话。数组不严格等于字符串，已有该服务会话绑定时会沿用旧绑定，也不会按 new 分支清除旧澄清内容。没有旧绑定时仍会创建会话，不能把问题描述为任何请求都复用旧会话。

2026-10-23 直接调用当前 `parseDecision()`，确认 `"new"`、`"continue"` 正常通过；`["new"]`、`["continue"]` 及 `[["new"]]` 也被错误接受，而返回值的类型仍是数组。对象、null、数字、布尔值和非法字符串的对照被拒绝。这是纯 JSON 解析及后续严格相等条件的离线复现，未用真实模型量化其出现频率，也未调用后端。

### 已确认的改法

用户于 2026-10-23 确认以下修复方案，同日已实施。

1. 在 [router/types.ts](../src/router/types.ts) 中，将上述字符串转换检查替换成直接严格比较：

   ```ts
   item.session === "continue" || item.session === "new"
   ```

   将这两个比较用括号作为 dispatch 条件的一部分。利用类型缩窄直接返回 `item.session`，移除该字段不必要的类型断言；不把数组纠正成字符串后继续执行。

2. 非法值返回 `null`，交给路由已有的格式纠正流程：最多再请求一次模型决定；仍无效则失败，不调用后端。不改变合法 new／continue 的会话规则，不增加新的重试循环。

3. 在 [router-decision.test.ts](../tests/router-decision.test.ts) 补真实解析函数的纯逻辑回归：合法字符串通过；数组及嵌套数组、对象、null、数字、布尔值、缺失字段和非法字符串被拒绝。覆盖 JSON 文本与直接对象两种现有输入形式，保留其他决定及字段约束的测试，不使用模拟模型或服务。

验收要求：解析成功的 dispatch 决定中 session 必须是两个合法字符串之一；畸形字段不能到达后端调用。源码、纯解析测试及路由 L2 已更新；现有一次纠正流程与后端调用位置未改，检查结果见验证记录。

## 5. B4：来源目录保留真实状态

### 当前问题与影响

本项发生在 chat 内部。程序将来源目录放进 [service.ts](../src/chat/service.ts) 的检索阶段系统上下文，供模型判断下一步是否搜索、读取或结束检索。它不是微信中显示的链接列表，也不是外层服务路由的会话状态。

[research.ts](../src/chat/research.ts) 的来源记录有以下状态：

| 状态 | 当前含义 |
|---|---|
| `unread` | 已登记 URL，但本轮尚未取得该来源的摘要或正文 |
| `summary` | 本轮已取得搜索摘要，尚未成功取得正文 |
| `read` | 已抓取并缓存正文；可能截断或仅向模型返回部分分页，不表示模型已读完整网页 |
| `failed` | 当前记录标记为读取失败；已有摘要时抓取失败会保留 summary，沿用现有规则 |

当前 `catalog()` 却把每条来源固定写成 `status: "unread"`。2026-10-23 从当前源码提取并运行原始目录映射，确认 unread、summary、read、failed 四种输入全部输出 unread，输入记录本身没有改变。

这使给模型看的目录与本轮工具结果不一致，可能导致重复读取或无效尝试，消耗模型／工具预算。不能据此断言模型每次都会重复抓取：它仍能看到真实工具结果；已有正文缓存时再次 read_source 会使用缓存，不再次调用 Fetch。实际影响频率尚未做真实模型评估。

### 已确认的改法

用户于 2026-10-23 确认以下修复方案，同日已实施。

只修改 [Research.catalog()](../src/chat/research.ts) 的目录投影，读取来源自身的 status，不写固定值：

```ts
catalog(): string {
  return JSON.stringify(
    this.sources().map(({ id, url, title, status }) => ({ id, url, title, status }))
  );
}
```

保留以下边界：

- 每个新问题建立新的 Research，上一轮来源只重新登记 ID、URL、标题，仍从 unread 开始；不能把历史正文或旧的 read 状态当成本轮已核实证据。
- 同一轮的首次检索和唯一一次补查共享 Research，因此目录应持续反映本轮实际状态。
- 不改变搜索／抓取后的状态写入、摘要与正文缓存、evidence() 的证据筛选或预算控制，也不增加联网调用。

验收范围：目录对四种状态原样输出且不改动记录；搜索摘要与正文读取后的目录状态和实际记录一致；新一轮重新登记旧来源仍为 unread，只有本轮实际获取后才进入证据；同轮补查保留现有状态。已完成实际纯数据投影、跨轮初始化、真实 Search／Fetch 后的目录核对与同轮缓存检查，未引入模拟模型／HTTP；模型是否因此减少重复调用仍需另做样本评估。
