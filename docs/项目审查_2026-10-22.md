## 1. 确认的问题

### B1 · P1：常见禁止搜索表达被反向判为必须搜索

位置：[chat/service.ts](../src/chat/service.ts)，第 83–88 行；下游第 262–270 行、第 102 行会继续强制要求外部证据。

`policy()` 只识别少量否定句，随后用“搜索／联网”等子串判断必须搜索。直接执行当前纯函数得到：

| 输入 | 实际策略 | 应有行为 |
|---|---|---|
| 不联网，只把这句话翻译成日语：明天见 | required | 不执行搜索／抓取 |
| 无需联网，解释以下代码 | required | 不执行搜索／抓取 |
| 不需要搜索，润色下面的文字 | required | 不执行搜索／抓取 |
| 把“联网搜索”翻译成英文 | required | 不应仅因引文中的词强制搜索 |
| 不要联网，翻译：明天见 | off | 不执行搜索／抓取 |

影响：用户明确禁止 Search／Fetch 时，程序反而开放工具并要求联网证据；可能额外搜索，也可能在模型正确选择直接回答时不断要求补搜。这里的禁止联网仅指搜索／抓取，Chat API 本身仍联网。

处理方向及现状见 [审查改进方案 B1](审查改进方案.md#2-b1默认由现有检索模型决定是否搜索)。表中的应有行为描述用户可见结果，不要求自然语言禁止表达必须转换为 off 参数；修复已删除关键词策略改写。

### B2 · P2：链接校验误拦截正常翻译、改写和页面锚点

位置：[chat/service.ts](../src/chat/service.ts)，第 90–99 行；URL 登记规范见 [chat/types.ts](../src/chat/types.ts) 的 `webUrl()`。

当前把答案中所有 HTTP(S) URL 都当作必须来自本轮外部证据的引用。翻译或改写用户提供的文字时，原样保留 `https://example.com/help`、本轮不搜索且证据为空，就会得到“链接不属于本轮已获取来源”。修复循环最终可能删去用户要求保留的网址，或只返回来源检查失败提示。

另一个已复现边界：已登记 `https://example.com/help` 时，答案给出 `https://example.com/help#setup [S1]` 仍被拒绝。登记时去掉 fragment，校验时没有使用相同规范化规则。

建议：分别处理用户提供的文字链接与模型声称作为事实依据的引用；前者不能冒充已验证资料，但也不应阻止忠实翻译。引用 URL 采用一致的规范化方法。

### B3 · P2：路由的 session 字段没有严格检查类型

位置：[router/types.ts](../src/router/types.ts)，第 32–34 行；消费位置：[router/router.ts](../src/router/router.ts)，第 114、126 行。

`parseDecision()` 使用 `String(item.session)` 检查枚举，却返回原始值。实际执行以下 JSON 会成功解析，并保留数组：

```json
{"action":"dispatch","serviceId":"chat","session":["new"]}
```

后续 `decision.session === "new"` 为 false。已有绑定时会沿用旧会话，而不是拒绝畸形决定并触发路由修正，可能把原应隔离的新任务带入旧上下文。`["continue"]` 也会被错误接受。

建议：先要求 `typeof item.session === "string"`，再检查枚举；对 JSON 数组、对象和其他类型添加纯解析回归。

### B4 · P2：来源目录把已读来源重新标成 unread

位置：[chat/research.ts](../src/chat/research.ts)，第 68 行；目录被 [chat/service.ts](../src/chat/service.ts) 第 209 行写进检索阶段系统上下文。

`catalog()` 无条件输出 `status: "unread"`。用原始序列化方法检查当前轮 `read` 和 `summary` 两条记录，目录输出都是 `unread`。上一轮来源重新登记为未读是合理的，但不应覆盖本轮已经取得的状态。

影响：系统上下文与实际工具结果相矛盾，模型可能重复阅读或过早用完工具预算。数据层正文并没有因此删除；额外调用发生频率尚未经真实模型量化。

建议：目录保留实际 status，继续让旧来源在新一轮登记时初始化为 unread。

## 2. 需要优先处理的限制与验证缺口

这些与上面的确定性错误分开：部分已在文档明确说明，不能当作刚发现的功能回退。

| 项目 | 当前证据与影响 | 建议 |
|---|---|---|
| 作答上下文重复装载资料 | `answerContext()` 同时装入完整来源摘要及全部工具结果。用 20 条各 2,000 字符的来源、4 页各 8,000 字符的正文检查原始序列化代码，尚未加系统提示就达到 76,647 字符，超过默认 60,000；代码会直接返回 limited。来源数与读取量各自都在默认预算内。 | 为最终作答分配独立资料预算；来源目录保留元数据，正文片段去重并按相关性裁剪。别只扩大总上限。 |
| 路由与 chat 输入上限不一致 | 路由接受 12,000 字符，chat 只接受 8,000。8,001–12,000 字符或累积澄清文本可在付出路由调用后被 chat 拒绝。 | 在服务能力契约中声明输入上限，并在调用前明确反馈；澄清文本也计入。 |
| 没有统一当前时间上下文 | 检索前的路由与 chat 提示没有注入当前日期／时区；取得来源后才有 retrievedAt。 | 注入明确日期与时区，减少“今天／今年／最新”查询选错时间的风险。未实测具体错误答案。 |
| 微信长回复 | 当前按 1,500 个 Unicode 字符硬切，可能拆开 URL、代码围栏或表格；手机端长回复尚未验收。 | 优先按段落／换行切分，避免截断链接，并实测多段送达顺序。 |
| 微信取消、清空与进度 | 主循环串行等待整轮完成；没有微信中的取消／清空命令或处理中提示。终端 Ctrl+C 可取消，独立 chat CLI 有 /clear，但这不代表微信支持。 | 先确定必要交互，再设计当前任务控制通道；仅增加“取消”文本分支不能中断正在阻塞的处理。 |
| 发送失败恢复 | 应用保留答案和段数，但结束后释放 replyHandle，且没有人工重发入口；重启清空。 | 恢复时使用用户新消息取得的有效渠道句柄，复用已生成答案，不重跑问答；部分发送和未知发送分别处理。 |
| 回归覆盖 | 38 项测试覆盖配置、决定解析、格式化与终端，不覆盖 chat 主循环、路由会话状态机或微信故障链路。真实 API 验收侧重 HTTP／状态／引用存在，不能证明翻译含义、追问继承或证据语义正确。 | 继续遵守不恢复模拟 HTTP／模型的要求：纯逻辑用离线回归；完整链路用明确的真实验收样例和人工核对。 |
| 最新工作尚未提交 | 大量当前实现修改以及 router、model 等新文件还在工作树，已删除测试也尚未提交。 | 修复验收后形成 Git 检查点；其他电脑不能仅靠旧提交恢复当前工作。本次未刷新远端。 |
