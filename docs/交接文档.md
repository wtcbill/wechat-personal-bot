## 1. 项目目标与开发入口

独立开发 Weave，以微信聊天窗口作为自然语言入口，远程调用自己的工具与服务。第一项后端能力先接 DeepSeek 文本问答，DSH、SSH 远端 Codex 等后续接入；先在本机 Windows 验证，再考虑服务器部署。

目标链路：`微信 / iLink → 应用入口 → 后端服务路由（AI 判断意图）→ 所选后端服务 → 共享回复格式化 → iLink → 用户`。

- 当前项目根目录：以本仓库的克隆位置为准；[仓库根目录](../)。原工作区路径仅作历史定位。
- 开发入口：[工作须知](工作须知.md) → [Weave 规则](../AGENTS.md) → [Weave L1](../L1.md)，按 [GEB 指南](GEB使用与维护指南.md) 维护实际实现地图。
- [首版方案](首版方案.md) 维护阶段范围与验收；[技术栈](技术栈.md) 维护技术选择；[README](../README.md) 维护当前行为与运行方法。
- `wechat-personal-bot` 保留为独立旧实现，不在其中续建 Weave；旧代码、配置、依赖和历史测试不自动成为新项目要求。已有修改保留，不搬动或覆盖。

## 3. 最新确认的架构边界

2026-10-21 用户确认以下分工，后续设计以此为准：

1. **后端服务路由**接收自然语言，调用 AI API 判断用户意图，选择已注册的服务并管理调用。程序校验模型返回的选择；意图不清时澄清。此前以人工选择或固定默认服务作为最终方案的建议已被替代。
2. **chat、DSH、SSH 远端 Codex 是并列后端服务**。路由位于这些服务之上，不默认广播请求，也不因某个服务失败自动换服务重做。
3. **此前讨论的搜索链路全部归 chat 服务内部**：chat 对话历史、直接回答／澄清／搜索判断、Search／Fetch、网页阅读、本地查找、补搜、预算控制、证据核对及回答整合。chat 不负责选择其他后端。
4. 路由 AI 与 chat AI 的提示词、上下文、结果契约和状态分别管理。可以共用供应商、模型或底层 API 客户端，但路由不通过调用 chat 业务服务来完成意图识别。
5. 微信协议与收发归渠道；访问校验、入站去重和回复协调归应用；共享回复格式化在 chat 外部。服务绑定及应用会话与后端会话映射归路由，chat 历史和搜索状态归 chat，各后端原生会话归各自后端。
6. chat 内部按用户要求分工：前面关闭思考，只做检索决策；作答开启思考，根据原问题与实际资料回答。思考发现关键缺口时，最多交回非思考检索阶段补查一次，再合并实际资料作答。无需搜索与澄清同样进入思考作答；思考阶段不直接执行工具，补查不能重置原预算或绕过禁止联网。具体契约和预算以 [chat L2](../src/chat/L2.md) 与源码为准。

chat 已按上述边界独立实现，上层路由仍未实施。保持模块隔离、高内聚低耦合；后端会话 ID、工具历史和压缩状态不假设可以互通。chat 历史仅在内存中、重启清空；其他状态是否持久化另行确定。

方案入口与事实归属：

- [整体架构草案](架构草案.md)：开头“已确认的整体分工”维护路由与各后端边界；后续物理目录、接口签名等仍是候选设计。
- [chat 服务方案讨论](Weave搜索问答方案讨论.md)：维护 chat 内部完整流程图、API、程序工具和 Codex／DeepSeek 模式比较。该文件保留原文件名，标题已改为 chat 服务方案讨论。
- [DeepSeek 搜索调研](DeepSeek搜索链路调研_2026-10-20.md)：公开资料与官方 Harness 源码证据；未取得官网完整后台实现，也未实测其搜索 API。不能据此宣称自建方案已优于官网。

4. 验收依次区分：替代渠道／后端的流程验证、真实 API 返回、iLink 接受发送、手机实际收到。完成当前阶段后再增加 DSH 等后端。
