# GEB 使用与维护指南

GEB 是本项目面向开发者和 Agent 的分层导航：从上往下定位任务，从实现往上检查影响，只更新事实发生变化的层。它随实际功能增长，开发规则和操作边界见 [AGENTS](../AGENTS.md)。

本指南用于 Weave，沿用旧项目的分层组织与增量维护规则，所有导航只指向本项目的实际文件。旧实现的职责、路径、依赖和测试结果不作为新项目事实；候选技术栈与模块方案在落地后才进入实现地图。

## 1. 信息归属

| 层／文档 | 维护内容 |
| --- | --- |
| [AGENTS](../AGENTS.md) | 开发入口、硬边界和维护要求 |
| [L1](../L1.md) | 当前仓库区域、整体链路、外部系统、状态及下层路由 |
| L2 | 真实模块的职责与非职责、输入输出、依赖、状态、失败边界、文件及测试入口 |
| 必要的 L2-2 | 稳定子能力的流程、文件归属和与兄弟能力的边界 |
| 文件头 L3 | 文件的输入、输出、归属及重要副作用和依赖 |
| [README](../README.md) | 用户功能、配置、启动和验证命令 |

候选设计、当前阶段和历史分别进入适用的设计文档、交接文档和项目日志；不往长期地图追加任务流水账。同一事实只设一个权威来源，其他位置提供必要摘要和链接。当前实现通过代码、配置和测试核对；明确的产品要求与实现现状分别判断。

## 2. 初建与按需加层

1. 项目开始先建立 AGENTS、README、L1 和本维护指南。尚无代码时如实说明，不把目标目录或候选依赖写成已存在实现。
2. 实际模块出现后建立简短 L2，至少覆盖职责边界、输入输出、依赖／状态、实现文件和验证入口；没有测试时明确尚缺验证，不创建虚假链接。
3. 核心源码文件与长期脚本随开发补合适的 L3。简单入口、包说明、配置和测试不机械补齐所有字段或层级。
4. 只有出现稳定、可独立说明的子能力，且需要明确文件归属、流程或兄弟边界时，才增加 L2-2。文件变多本身不是加层依据。
5. 新的顶层职责或独立目录入口才评估新增 L2 和 L1 路由。物理目录与逻辑职责不必一一对应；共享类型按职责归属，不自动建立公共模块。

本项目当前只有开发文档和 [L1](../L1.md)，尚无业务模块、源码或测试，不建立 L2、L2-2 或 L3 占位。iLink、DSH 等能力按实际落地后的契约、状态和测试补图，不照搬旧项目或其他项目的模块划分。

## 3. 每次任务的执行流程

1. 阅读适用规则，确认实际项目目录；已初始化 Git 时核对真实仓库、分支和工作树，区分已有修改与本次范围。尚未初始化时如实说明，不借用上层或旧项目的仓库状态。
2. 明确当前目标和验收方式，经 L1 选择相关 L2，必要时进入 L2-2，再读目标 L3、代码和测试；用文件名、符号和关键词定向搜索。
3. 沿调用方与依赖核对输入输出、异常、副作用和状态；不要凭函数名或注释推断“只读”或“无网络”。
4. 用简短计划说明实现范围、可能影响的地图和验证方式，再修改。
5. 完成后从 L3 向上检查；只修改事实变化的层，并同步相关用户或操作文档。

地图与实现不一致时，先核实是说明过时还是实现偏离需求。GEB 维护不自动授权重写、文件迁移、安装或外部操作，具体范围遵循用户当前要求。

## 4. 改动与同步范围

| 改动 | 必要检查与更新 |
| --- | --- |
| 局部算法修复，契约和副作用不变 | 修改实现与相关测试，核对 L3；上层事实不变则保持原文 |
| 新增核心源码或长期脚本 | 补合适的 L3，在直接所属地图登记入口与验证位置 |
| 参数、返回值、异常或副作用改变 | 更新 L3；涉及模块契约或流程时更新相应 L2-2／L2 及消费者说明 |
| 移动、重命名或删除文件 | 检查导入、动态引用、资源路径和测试定位，同步 Pos、成员清单及双向链接 |
| 职责、依赖、状态或失败边界改变 | 更新相关模块地图；系统链路、外部系统或顶层路由变化再更新 L1 |
| 新增稳定子能力 | 按真实职责评估 L2-2，调整直接父地图与文件归属 |
| 用户能力、配置或操作变化 | 更新 README 或对应专项说明；地图只保留职责摘要和链接 |
| 阶段完成或验证状态变化 | 更新适用交接；详细过程进入日志，不将测试数量或提交状态抄进各层地图 |

“向上检查”不等于“逐层修改”，无需在未变化地图中追加“本次已检查”。只有用户任务包含整理时才移动文件，不为符合地图布局顺手迁移实现。

## 5. L3 文件头

核心源码和长期脚本使用下列信息，内容须符合实际行为；根据选定语言使用合法注释语法，可以沿用原文件的注释语言：

```text
L3
Input: 调用方提供的参数、配置、数据或状态。
Output: 实际返回值、可观察输出及重要异常。
Pos: 所属职责、本文件作用及直接地图相对路径。
Effects/Dependencies: 文件、网络、缓存、进程或平台调用及关键依赖。
```

- L3 只在源码文件头维护，地图链接源码，不另建需要实时同步的文件头总表。
- 区分导入、调用和启动时的行为，以及经依赖间接触发的 I/O；如 `--check` 与正常启动有不同副作用，应准确说明。
- 保留编码、BOM、shebang／编码声明、模块 docstring 和 future import 的语法要求；为其他语言使用合法注释格式。
- 简单包入口可以保持原有简短说明；普通 Markdown、JSON、测试样例和生成物不强制套用源码模板。

## 6. 完成条件与验证

- [ ] 实现与相关测试满足当前目标；接口、状态与副作用说明符合实际代码。
- [ ] 新文件已读取检查；新增核心实现有适当坐标，并可从直接所属地图找到。
- [ ] 已沿 L3 → 必要的 L2-2 → L2 → L1 检查，只同步事实变化的层及必要专项文档。
- [ ] 路径、相对链接、锚点、文件归属及向上入口有效；正式地图不依赖仓库外草稿或本机绝对路径。
- [ ] 已检查限定差异，保留用户已有修改；真实配置、私聊数据、密钥、缓存和构建产物未误入交付。
- [ ] 已执行、未执行、失败或受阻的验证如实说明；历史结果不冒充本轮结果。

纯文档或注释修改检查路径、链接、符号和差异；文件头修改额外验证语法、原有正文与 docstring 未变。功能修改执行相关测试，契约、持久状态、平台收发或部署影响扩大时再扩大验证；验证现状与落地后的实际命令由 [README](../README.md#测试) 维护。

链接检查只能证明目标存在，不能证明职责描述正确；仍需核对关键实现。模拟测试、配置检查、真实模型调用和微信送达分别记录，不互相替代。当前先使用必要的静态检查，后续按实际需要增加自动检查。
