# Weave 首版方案

状态：首版范围、使用规则和技术栈已确认。本文维护产品边界与阶段验收；技术选择以 [技术栈](技术栈.md) 为准，实现与运行入口见 [README](../README.md)。

## 1. 产品方向与首版范围

长期方向：以个人微信聊天窗口作为交互终端，通过 iLink 接入应用，远程使用用户部署的工具与服务；各服务作为独立适配器接入。

用户已选择自然语言交互。首版只接入 DS API（DeepSeek API），先跑通文本问答；DSH、SSH 远程执行及其他后端放到后续版本。

已确认使用规则：只有用户本人使用，先在本机 Windows 运行；聊天历史仅在内存中，重启不保留。登录凭据和消息游标属于渠道状态，可在本机单独保存。

首波先验证微信收发：扫码登录者为唯一允许的用户，其私聊发送“你好”时回复“收到”。其他用户、群消息和非文本消息均不处理；本阶段不调用模型。DeepSeek 问答属于后续阶段。

当前先接入的后端能力为 `chat` 服务，以 DeepSeek API 完成文本问答。2026-10-21 用户进一步确定目标架构：上层“后端服务路由”通过 AI API 理解自然语言意图并选择服务；chat、DSH、SSH 远端 Codex 为并列服务。chat 内部独立管理直接回答／搜索的判断及整条搜索整合链路，不与上层服务路由混合。这取代此前将“固定后端、不增加路由 AI”作为整体目标的限制；路由模型和接口仍待确定。

当前微信应用仍为 iLink 固定回复；独立 chat 服务已实施模型问答和内部搜索链路，通过公共接口与本机 CLI 调用，尚未装配上层路由或微信问答。当前实际入口见 [README](../README.md#chat-本机问答与搜索)；不提前实现文件操作、代码执行或通用任务规划框架。

## 2. 最小链路

`本人微信中的机器人会话 → 腾讯 iLink → 应用入口 → 后端服务路由（AI 意图识别）→ chat 服务 → 应用回复协调 → 回复格式化 → 腾讯 iLink → 本人微信中的机器人会话`

这是当前 iLink 接入方式下的后续 DeepSeek 问答目标链路。当前首波链路为：`本人微信中的机器人会话 → 腾讯 iLink → 本机 Weave 本人限制与固定回复 → 腾讯 iLink → 原机器人会话`。实现完成、模拟通过、真实服务接受发送与用户确认微信送达分别记录。

已验证的入口是微信内的 OpenClaw/机器人会话，不是将普通微信小号作为好友交给 Weave 控制，也未验证普通好友收发。Weave 独立请求腾讯 iLink 服务，本机没有运行 OpenClaw 宿主。普通好友入口若是产品的必要条件，需要单独评估渠道，不能由此次收发验收推出其已可用。

用户已进一步明确希望采用普通微信好友入口，并确认有可在本机登录的小号。当前仅完成候选方案调查，未确定或实施桌面桥接方案。本次版本保存已验证的机器人入口，普通好友入口作为后续独立阶段。

## 3. 模块边界

以下是目标逻辑职责，实际落地情况见 [L1](../L1.md)，不为尚未实现的能力创建占位模块。

| 职责 | 负责 | 隔离要求 |
| --- | --- | --- |
| 公共契约 | 应用消息、问答请求、结果、错误及后端接口 | 保持轻量，不含渠道协议、具体 SDK 或 HTTP 实现 |
| 微信渠道 | iLink 接入、消息转换、渠道状态和实际收发 | 不调用模型，不决定模型配置或上下文策略 |
| 应用入口与回复协调 | 接收输入、执行访问与去重策略，通过服务路由协调处理和回复 | 依赖公共接口，不进入具体后端业务 |
| 后端服务路由 | 调用 AI API 理解自然语言意图、选择后端、管理绑定并发起调用 | 不使用 chat 业务服务完成路由，不调用 chat 内部搜索工具 |
| chat 服务 | 管理本服务对话、直接回答／搜索选择、工具循环与信息整合 | 独立于服务路由，与 DSH／远端 Codex 平级；搜索设计属于内部能力 |
| 模型与搜索适配器 | 在所属模块内封装认证、API 请求、响应解析、超时与错误转换 | 路由与 chat 可复用底层客户端，但业务上下文分开；不认识微信原始消息 |
| 回复格式化 | 将应用结果整理成可发送的文本，处理分段与用户可读错误 | 不发起模型调用，不管理渠道连接 |
| 启动装配 | 加载配置、构造对象、注入具体实现、启动与关闭 | 在此选择适配器，不积累业务处理逻辑 |

具体适配器之间不互相导入。协议字段、SDK 对象和服务专有异常在各自适配边界内转换；应用通过公共结果与错误处理流程。

将来增加 DSH 等后端时，主要增加适配器、装配与配置；新增能力确实需要公共接口变化时，再显式扩展接口并核对调用方，不提前建立覆盖所有未来能力的框架。

## 4. 验收条件

首波：

1. TypeScript 类型检查、模拟测试、编译和离线配置检查可运行。
2. 本人扫码登录，程序从登录结果取得本人身份；缺少身份时拒绝启动收发，不采用“首个发消息的人”作为本人。
3. 本人在手机微信对应会话发送“你好”，看到“收到”；同一进程内重复投递同条消息不重复发送，其他用户、群与非文本不触发回复。
4. 登录凭据及游标仅保存在本机忽略目录，聊天正文不落盘；取消和重启行为明确。

后续 DeepSeek 问答：

1. 允许接入的微信用户发送一条自然语言文本，经 iLink 和 DeepSeek API 得到回复，并回到对应聊天窗口。
2. 模型请求失败或超时时有可读反馈，后续消息仍能继续处理；重复接收同一消息时不重复执行同一问答。
3. 不连接微信、不调用真实 API，也能通过替代渠道与后端实现验证应用主流程及主要失败路径；替换具体后端实现无需修改微信收发代码。
4. 模拟测试、配置检查、真实 API 调用和微信送达分别记录结果；真实链路跑通后再开始增加其他服务。

## 5. 后续待定

技术选择见 [技术栈](技术栈.md)。以下参数在相应功能开始前确定：

- chat 当前模型、非思考参数、超时和默认预算见 [chat 模块](../src/chat/L2.md)，真实样本验证后再调整；路由 AI 参数不复用 chat 业务配置。
- 路由 AI 的模型、服务说明与结构化选择契约、服务绑定及切换规则；AI 自然语言选择服务的方向已确定。
- DeepSeek 阶段的消息去重保留期限、任务状态与发送恢复策略。当前收发去重规则见实际模块说明。
- 是否在下一阶段支持多轮，以及会话划分、裁剪和清空交互。若实现多轮，会话管理归 API 对话能力，与 DeepSeek 调用分离；历史在内存中，重启清空。32k 或 300k 均未确认为预算。
- SQLite 具体驱动、确需持久化的处理状态及恢复语义；不因此保存聊天历史。
- 本机稳定运行后的服务器部署安排。

开发规则见 [AGENTS](../AGENTS.md)，当前实际文件地图见 [L1](../L1.md)，分层维护按 [GEB 指南](GEB使用与维护指南.md) 执行。本文的候选模块划分与待定事项不作为已实现结构。
