# Weave 首版方案

状态：首版范围、使用规则和技术栈已确认，微信与终端的真实问答主链路已打通。本文维护产品边界与验收要求；技术选择以 [技术栈](技术栈.md) 为准，实现与运行入口见 [README](../README.md)，最新验收记录及已知问题见 [项目交接](交接文档.md)。

## 1. 产品方向与首版范围

长期方向：以个人微信聊天窗口作为交互终端，通过 iLink 接入应用，远程使用用户部署的工具与服务；各服务作为独立适配器接入。

用户已选择自然语言交互。首版只接入 DS API（DeepSeek API），先跑通文本问答；DSH、SSH 远程执行及其他后端放到后续版本。

已确认使用规则：只有用户本人使用，先在本机 Windows 运行；聊天历史仅在内存中，重启不保留。登录凭据和消息游标属于渠道状态，可在本机单独保存。

早期微信收发验证已结束，固定回复诊断已按用户要求删除。当前只保留真实文本问答，扫码登录者为唯一允许的用户；其他用户、群消息和非文本消息均不处理。

当前接入的后端为 `chat` 服务，以 DeepSeek API 完成文本问答。上层“后端服务路由”通过独立 AI API 调用理解自然语言意图并选择服务；chat、DSH、SSH 远端 Codex 在目标架构中是并列服务，当前仅 chat 已接入。chat 内部独立管理直接回答／搜索的判断及整条搜索整合链路，不与上层服务路由混合。首版路由与会话契约已落地，具体配置以源码与 README 为准；架构决策过程保留在项目日志。

微信默认启动已接通真实问答，旧 `--mode routed` 参数兼容。chat 已实现问答、内部搜索和有限内存多轮，终端与微信共用真实路由、通用应用和回复格式化。主链路已通过受控样本及手机收发验证，具体覆盖范围见 [项目交接](交接文档.md#4-当前验证与下一步)。当前入口见 [README](../README.md#路由调试与-api-配置)；不提前实现文件操作、代码执行或通用任务规划框架。

按用户要求，模拟实现、使用模拟 HTTP／模型的自动测试及固定回复诊断已删除。`--debug` 进入真实终端对话，普通启动进入真实微信问答。搜索回复只展示正文和必要限制，隐藏内部来源编号，不自动列出全部来源；明确索要的相关链接可保留。工程测试与真实 API 验收分开，使用与退出方式以 README 为准。

## 2. 最小链路

`本人微信中的机器人会话 → 腾讯 iLink → 应用入口 → 后端服务路由（AI 意图识别）→ chat 服务 → 应用回复协调 → 回复格式化 → 腾讯 iLink → 本人微信中的机器人会话`

这是当前已实现的 iLink 问答链路。默认启动与终端调试共用通用应用和真实后端；工程检查、真实 API 调用、渠道受理发送与用户确认微信送达分别记录。

已验证的入口是微信内的 OpenClaw/机器人会话，不是将普通微信小号作为好友交给 Weave 控制，也未验证普通好友收发。Weave 独立请求腾讯 iLink 服务，本机没有运行 OpenClaw 宿主。普通好友入口若是产品的必要条件，需要单独评估渠道，不能由此次收发验收推出其已可用。

用户已进一步明确希望采用普通微信好友入口，并确认有可在本机登录的小号。当前仅完成候选方案调查，未确定或实施桌面桥接方案。本次版本保存已验证的机器人入口，普通好友入口作为后续独立阶段。

## 3. 模块边界

以下是目标逻辑职责，实际落地情况见 [L1](../L1.md)，不为尚未实现的能力创建占位模块。

| 职责 | 负责 | 隔离要求 |
| --- | --- | --- |
| 公共契约 | 应用消息、问答请求、结果、错误及后端接口 | 保持轻量，不含渠道协议、具体 SDK 或 HTTP 实现 |
| 微信渠道 | iLink 接入、消息转换、渠道状态和实际收发 | 不调用模型，不决定模型配置或上下文策略 |
| 应用入口与回复协调 | 接收输入、执行访问与去重策略，通过服务路由协调处理和回复 | 依赖公共接口，不进入具体后端业务 |
| 后端服务路由 | 调用 AI API 理解自然语言意图、选择后端、管理绑定并发起调用 | 不使用 chat 业务服务完成路由，不调用 chat 内部搜索工具 |
| chat 服务 | 管理本服务对话、直接回答／搜索选择、工具循环与信息整合 | 独立于服务路由，与 DSH／远端 Codex 平级；搜索设计属于内部能力 |
| 模型与搜索适配器 | 在所属模块内封装认证、API 请求、响应解析、超时与错误转换 | 路由与 chat 可复用底层客户端，但业务上下文分开；不认识微信原始消息 |
| 回复格式化 | 将应用结果整理成可发送的文本，处理分段与用户可读错误 | 不发起模型调用，不管理渠道连接 |
| 启动装配 | 加载配置、构造对象、注入具体实现、启动与关闭 | 在此选择适配器，不积累业务处理逻辑 |

具体适配器之间不互相导入。协议字段、SDK 对象和服务专有异常在各自适配边界内转换；应用通过公共结果与错误处理流程。

将来增加 DSH 等后端时，主要增加适配器、装配与配置；新增能力确实需要公共接口变化时，再显式扩展接口并核对调用方，不提前建立覆盖所有未来能力的框架。

## 4. 验收条件

首版统一验收以下要求，不再将已接通的 DeepSeek 问答列为后续接线任务：

1. TypeScript 类型检查、纯逻辑／实际终端测试、编译和离线结构检查可运行；真实 API 验收显式触发，不混入默认离线测试。
2. 本人扫码登录，程序从登录结果取得本人身份；缺少身份时拒绝启动收发。其他用户、群与非文本不触发后端或回复。
3. 本人文本经独立路由进入 chat，完成直接问答、连续追问或搜索／原文读取后的思考作答，并回到对应微信会话。终端可独立于微信调试同一后端链路。
4. 模型失败、超时和取消有明确状态，后续消息能继续处理；在应用去重记录有效范围内，重复投递不重复执行或发送。缓存淘汰、重启和未知发送回执的限制须明确，不能承诺跨进程恰好一次。
5. 登录凭据及游标仅保存在本机忽略目录，聊天正文不落盘；后端结果与发送状态分开，发送失败不自动重跑问答。

已完成的受控验收包括离线工程检查、终端真实问答／追问／搜索读取，以及微信普通问答和搜索回复的手机确认。待补验收包括长回复分段、补查、超时／取消、发送失败及恢复、复杂意图和引用语义；已实现并不代表所有异常分支都已实测。具体记录与已知缺陷统一见 [项目交接](交接文档.md#4-当前验证与下一步)。

## 5. 后续待定

技术选择见 [技术栈](技术栈.md)。现有默认参数和状态规则由对应模块维护，后续工作包括：

- 校准 chat 的检索／作答预算与资料裁剪策略；当前思考模式、模型、超时和默认预算见 [chat 模块](../src/chat/L2.md)。
- 扩展路由的意图、澄清和会话选择验收；现有路由到 chat 的实际可用性已通过受控样本。其他后端接入时单独确定权限与服务配置，见 [路由模块](../src/router/L2.md)。
- 设计人工重发和发送恢复交互。已有去重期限、内存结果与发送状态见 [应用模块](../src/L2.md#职责契约与状态)，不把这些既有规则重新列为待定。
- 完善多轮上下文、指代和会话控制。有限内存多轮与裁剪已实现；独立 chat CLI 有清空入口，微信／路由终端的清空交互、微信取消与进度提示尚未实现。历史仍仅存内存，重启清空。
- 明确 SQLite 驱动、确需持久化的处理状态及恢复语义；不因此保存聊天历史。
- 在本机稳定运行后确定服务器部署，以及普通好友渠道、新后端的独立实施阶段。

开发规则见 [AGENTS](../AGENTS.md)，当前实际文件地图见 [L1](../L1.md)，分层维护按 [GEB 指南](GEB使用与维护指南.md) 执行。本文的后续事项不作为已实现能力。
