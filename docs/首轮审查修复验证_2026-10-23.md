## 澄清误拦截后续修复

用户要求只修第一个问题，日期问题不处理。本阶段删除了输出检查中通过问号、少量中英文词语和句号排除规则推断澄清的逻辑。

思考作答协议新增 `{"action":"clarify","answer":"需要用户补充的条件"}`。解析器严格校验字段、字符串、非空和 300 字符上限；输出检查依据作答阶段的显式决定接受澄清，不依据检索决定或正文措辞。澄清可在没有外部证据时提问，已有资料时也不强制附带引用；如果包含来源 ID 或 URL，仍须通过原归属检查。普通 answer 在 required 下依然必须有本轮外部证据，并在已有资料时包含有效引用。模型标记本身不证明内容在语义上一定是纯提问；提示词要求只索取缺少的条件，不混入未核实结论。

本阶段验证：

- 真实纯函数局部回归 25 项通过；新增覆盖中文不同句式、句号／无标点、英文、非法或超长 clarify、普通问句不能绕过 required、澄清中的无效来源／URL 仍被拒绝。没有模拟模型或 HTTP。
- `npm.cmd run check`：类型检查、5 个文件共 82 项测试、构建通过。
- `npm.cmd run test:review-api`：9 个真实模型样本与 Research 状态／缓存检查全部通过。以普通天气请求替换了固定提问用例，并增加另一中文表达和英文表达，均未指定答案措辞。
- 三条真实澄清分别为“请告诉我你要查询的城市或地区，以及具体日期或时段（例如：上海，今天下午）。”、“请告诉我你所在的具体城市或地区，我才好帮你查当地天气。”和“What location should I check the weather for, and for what date or time period?”。均由检索 clarify 转入思考 clarify，completed，未发生 Search／Fetch；相关模型调用均 HTTP 200。
- `npm.cmd run test:api`：原有三项路由到 chat 的直接问答、同会话追问、实际 Search＋Fetch 及引用均通过。
