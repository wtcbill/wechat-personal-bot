## 2. 项目背景与读取到的状态

项目名为 Weave。方向是以微信聊天窗口作为交互入口，通过 iLink 接入应用，再调用用户部署的工具与服务。

本次较早读取的 main 分支中，README、AGENTS、L1 和首版方案显示：

- 首版只接 DeepSeek API，先跑通自然语言文本问答。
- DSH、SSH 远程控制等放到后续版本。
- 首版应用通过公共后端接口调用 DeepSeek 适配器，不提前做跨后端智能路由或通用任务规划器。
- 首版不实现文件操作、代码执行和搜索工具。
- 当时仓库只有文档，没有业务源码、依赖声明、运行配置或可执行测试。
- 模拟测试、真实 API 调用和微信送达需要分别验证。

以上是本次读到的文档快照，不代表交接时仓库仍处于同一状态。Codex 应重新核对实际文件与 Git 状态。〔DOC001〕〔DOC002〕〔DOC003〕〔DOC004〕

## 4. 隔离与模块边界

用户重视模块清晰、高内聚低耦合、实现可替换。本次讨论沿着仓库已有的职责隔离方向继续澄清，没有确定物理目录或接口签名。〔T01::M003〕〔T01::M004〕〔DOC002〕

| 职责 | 负责 | 边界 |
| --- | --- | --- |
| 微信渠道适配器 | 登录、收发、原始消息转换、渠道凭据和收消息游标等渠道状态 | 不直接调用 DeepSeek，不决定聊天历史裁剪策略 |
| 应用服务 | 接收统一消息、访问与去重策略、协调处理和回复 | 通过公共接口调用能力，不依赖微信协议或具体模型 SDK |
| API 对话能力 | 管理该能力的会话与历史，组织一次问答 | 会话策略与具体 HTTP/SDK 调用分开 |
| DeepSeek 适配器 | 认证、请求格式转换、调用 API、响应解析、超时与错误转换 | 不直接向微信发送消息 |
| 回复格式化 | 将结果整理成可发回微信的文本、分段和可读错误 | 不执行模型调用 |
| 启动装配 | 读取配置、构造并注入实现、启动和关闭 | 不积累问答业务逻辑 |

### 隔离的具体含义

- 微信适配器与后端适配器不直接互相依赖，由应用服务协调。
- 后端适配器内部需要了解具体服务；它负责把这些细节挡在应用逻辑之外。
- 使用现成 SDK 与编写适配器可以同时成立：SDK 封装服务调用，适配器负责将该 SDK 接入 Weave 的公共契约。
- 更换微信接入实现时，尽量不改问答处理；更换问答后端时，尽量不改微信收发。
- 可替换实现不仅要函数名称一致，还要满足请求、结果、错误和状态行为的约定。
- “独立模块”不等于“独立服务器”。助手建议首版在同一进程内通过接口调用，不为每种职责先建一个网络服务。
- 职责可以先用少量文件和简单接口表达，不要求为每种职责创建复杂目录或框架。

上述为讨论中的设计方向；具体实现仍需与代码和测试核对。

### API 对话模块中的多轮会话

用户提出“应该是api对话模块吧”，助手认可：首版 API 问答的多轮上下文可放在 API 对话模块中，内部区分会话管理与 DeepSeek 调用。具体组织方式尚未实现。〔T01::M011〕〔T01::M012〕

- 会话管理：会话识别、历史保存、裁剪、清空和重启恢复策略。
- DeepSeek 适配器：将准备好的对话请求转换成具体 API 调用并返回统一结果。
- 应用总入口负责协调，不分散保存所有聊天历史。
- 微信回复所需的渠道令牌，与模型聊天历史是不同状态。
- 后续 DSH 的会话可以由 DSH 能力管理，不强行共用 API 聊天历史，也不提前把所有后端塞进同一个问答接口。

## 5. 接入方式与已经澄清的概念

### iLink、SDK、适配器不是同一层

iLink 是微信接入协议，不是仅限 Python 的 SDK。Python SDK 可以封装这套协议；腾讯公开参考插件使用 TS。本次没有确定具体使用哪个 Python 或 TS SDK，也没有验证普通小号场景和实际登录、收发。〔EXT001〕

微信适配器是 Weave 自己的模块，内部调用选定的库或 HTTP 接口，对应用提供统一消息与收发能力。不能把腾讯 OpenClaw 插件直接等同于可独立导入的通用 TS SDK，实施时需要核对依赖与可复用边界。

### DeepSeek API 可以直接用 TS 调用

简单问答不需要经过 Python。DeepSeek 官方文档有 Node.js 调用示例，使用 OpenAI SDK 配置 DeepSeek 的服务地址与密钥，实际请求的是 DeepSeek 服务。具体模型、参数、超时和输出限制仍未确定。〔T01::M006〕〔EXT002〕

### DSH 有 TS 客户端

本次查到官方仓库中的包名为 @deepseek-ai/dsh-sdk-client。TS 客户端和 Python SDK 通过同一套 JSON-RPC 协议控制 DSH 运行时；DSH 作为子进程运行，通过标准输入输出通信。TS 客户端需要配套运行时或显式指定可执行文件。〔EXT003〕

这只能支持“有 TS 接入方案”，不能据此声称已验证发布包、版本兼容、取消行为或微信到 DSH 的执行链路。DSH 继续保持后续版本范围。

### 主干 TS 允许接入 Python 或 C 工具

用户询问过工具层接 Python、C 应用提供 TS SDK 的可能性。讨论确认了两种通用方式：HTTP 接口与子进程输入输出；跨语言通信由对应适配器封装。〔T01::M006〕〔T01::M009〕

HTTP API 是程序调用入口，不必制作供人浏览的网页；同机程序也可以使用本机 HTTP 地址通信。SDK 使用的语言与服务内部实现语言可以不同。语音转写、图片压缩等只用于解释概念，没有因此被加入 Weave 的首版范围。

## 6. 多轮上下文：仍待确定

用户询问了 300k token 的数量和是否合适，没有确认最终预算。300k 等于 300,000 tokens；按字数换算只能作参考，实现时应使用适用的分词方式和 API 返回的用量。〔T01::M013〕〔EXT004〕

助手最后给出的建议是：

| 场景 | 建议预算 |
| --- | ---: |
| 日常连续聊天 | 默认 32k |
| 较长项目讨论 | 按需 64k |
| 长文档或完整记录分析 | 按需 128k～300k |

**以上数字都是建议，不是确认配置，也不代表某个模型已验证支持的窗口大小。** 用户尚未确定是否支持全部场景。〔T01::M014〕

另外建议：历史可以存入数据库，每次选取预算内的内容发送；不必因为窗口大就每次带上全部历史。系统提示、历史、当前问题及输出预留需要按模型实际限制统筹。历史摘要、检索补回和清空交互都没有确定具体方案。

## 7. 可靠性建议、待定项与后续衔接

### 助手提出过的实现建议

这些建议尚未实现，也不应写成测试结论：

- 收消息与模型处理分别运行，等待模型时仍可接收新消息。
- 同一会话顺序处理；不同会话以后设置有限并发。
- 区分已接收、处理中、已生成回复、已发送等状态。
- 模型已成功而微信发送失败时，尽量重发保存的结果，避免重复调用模型。
- 先验证微信接收与回传，再验证应用主流程和失败路径，之后接真实 DeepSeek 问答。
- 用替代渠道与后端验证主流程，再单独验证真实 API 和微信送达。

### 仍需讨论或核对

1. Node.js 运行版本、包管理器、依赖和启动命令。
2. TS 微信适配器采用哪个库或哪些直接 HTTP 调用；实际登录身份、会话入口和收发限制。
3. 公共消息、请求、结果与错误契约，以及目录划分。
4. DeepSeek 模型、思考模式、流式或非流式、超时与重试。
5. 允许哪些微信用户接入、重复消息标识与保留期限。
6. 首版是否包含多轮对话；会话划分、历史预算、持久化、重启与清空策略。
7. 是否采用 SQLite，如何记录处理状态与失败恢复。
8. 长回复分段、日志脱敏、本机运行与后续部署方式。
